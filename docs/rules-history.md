# Idlewick working instructions

Read HANDOFF.md for current product decisions and architecture before changing the game.

- Fresh-start design (owner, 16 November 2026): judge new progression from a new character first. Current testers are willing to restart; legacy behaviour must not dictate the design. Preserve compatible saves where practical, and never silently erase a hero. Any necessary reset must be explicit.

- Integration gate (owner, 16 November 2026): do not replace or substantially rebuild a skill/system in the playable build before checking its connections to other systems. Audit dependencies first, then validate candidate changes in isolated test saves before enabling them. Cover existing saves and earned progress, unlock reachability, ingredient/source routes, quests, inventory/bank conservation, shop transactions, companions, offline work and relevant UI journeys. Preserve existing working behaviour while candidates are under test. Passing render checks alone is insufficient; report unresolved failures and testing limits explicitly.

- `main` is the sole working and delivery branch. The redundant `work` branch was removed after verifying identical history. Pull from and push to `main`; do not recreate `work`.

- The source is index.html, js/ and css/. Play Idlewick.html is generated; rebuild it with `python3 scripts/package-game.py` after changes.
- Browser tests use Playwright's bundled Chromium unless `CHROMIUM_PATH` is set, read `IDLEWICK_URL` (default the preview on port 8765) and write screenshots to `SHOT_DIR` (default the OS temp folder). Never hard-code a machine's browser path, port or folder. Run the whole suite before merging, not only the tests for the area you touched: on 20 Nov nine tests had gone stale because later commits changed behaviour without running them.
- Run `node tests/regression.cjs` for engine, persistence, notifications, project pins and onboarding. The test uses only Node built-ins.
- Preview with `python3 scripts/preview.py`. Use `--host 0.0.0.0` only when the cloud preview needs it. Windows uses `py` instead of `python3`.
- Preserve the illustrated task cards and large visible action target. The user explicitly rejected replacing the game with dropdown selectors. Keep the tree and logs, ore-bearing rocks, crafting output and actual enemy visible.
- No dropdowns or collapsed disclosures anywhere. Use visible wrapping buttons, tabs and illustrated cards.
- Design size is 1920 × 1080. On desktop (> 860px) `js/scale.js` zooms the page by innerWidth / 1920, capped at innerHeight / 1080 when that is larger than 1 (ultrawide screens gain width, not giant text; `html.lw-wide` over 2300 page pixels), times Settings → Interface size (90/100/115%), and never below 85% (MIN_ZOOM): wider screens scale up, laptops (1280–1600) stop at 85% and the layout adapts (`html.lw-1600` / `html.lw-1300` for page widths under 1600 / 1300) instead of shrinking text further. Readability floor: no visible text under 13px in the design (so ≥ 11 screen px at 85%); `tests/ui-fit.cjs` checks this at 1280 × 720. CSS desktop breakpoints between 861 and 1920 were collapsed to 860/861; use `--vh`/`--vh100`/`--vw100` instead of vh/vw, `html.short` for scaled heights under 940px, and `DQ.toPage()` to convert screen coordinates (getBoundingClientRect, mouse) into page pixels. Phones (≤ 860px) stay responsive at 100%.
- Desktop shell (one-screen overhaul, approved concept): the page menu (Home, Quests, World, Village, Hero, Guide, Shop) lives in the top bar (`#topnav`, `js/shell.js`); the 180px left column holds the Now card (current task, Stop/Retreat), Combat and every skill. Phones keep the bottom bar and the task strip in the top bar. Do not move page links back into the left column.
- Keep the 180px desktop rail. Skill rows show icon, name, level or lock and one progress bar. Since Dec 2026 the rows share the window's height (`UI.fitDock` in js/shell.js sets `--dk-h`, 34–64 page px each), so the column reaches the bottom of the window at any size; `tests/return-and-rail.cjs` checks it. The older fixed sizes below (44px, 36px under `rail-tight`) are only the fallback; exact XP lives in the row's hover/focus detail, so every skill fits at 1440 × 900 without crushing rows. On windows shorter than 1180 page pixels (`html.rail-tight`, with 17 skills) rows tighten to 36px and the Now card to two lines so the column never scrolls down to 720px tall; skill emblems stay 32px (whole-number pixel scale). Never shrink text to fit within the 1920 design.
- Choice cards stack: picture on top (64px art box), then name, one short caption and state, centred. Locked cards show the blacked-out picture, ??? and a short requirement (e.g. "Lv 26 · Reach Saltmere"); the full wording lives in the tooltip and beside the scene when selected. Do not put text in a narrow column beside the art.
- On desktop activity pages (gather, make, farm) the page never scrolls: the action panel stays still and only the list of choices scrolls inside its panel. Every other desktop page also locks to the window (the content area scrolls only as a last resort): Quests is a scrolling list of rows beside the selected quest in full; Scholarship, Exploration, Shop, Map and Skill levels scroll only their long list; Combat follows **layout E** (see its bullet below) with the equipped paper doll beneath Where to fight. Nothing you act on may sit in a scrolling box and the fighters must stay inside the stage: `tests/ui-fit.cjs` checks both at 1280 × 720 with every ability unlocked. Rule from the player (Nov 2026): anything you act on stays on screen; only useful-but-not-actionable information may sit behind a click (combat level breakdown, full ability list, preparation, boss card, loot). Each button shows its state with a warning tone where attention is needed, so most checks need no click. Keep obvious text minimal. House: cottage, bonuses and room buttons on the left; the chosen room's furniture as cards on the right. Page tabs, the "Back to …" link and pinned quests share one `#pagebar` row. `node tests/ui-fit.cjs` enforces this.
- Backdrops (`js/backdrop.js`): code-drawn pixel scenes behind the game under a theme wash, with slightly see-through panels. Outside combat the player picks Starlit hills (default) or Twilight forest in Settings; Combat shows a scene for the area being fought or previewed (two per region, keyed by area id such as `saltmere:1`). Add a recipe there for any new area.
